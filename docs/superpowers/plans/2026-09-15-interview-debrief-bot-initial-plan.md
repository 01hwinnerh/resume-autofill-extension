# 面试复盘辅助机器人初步实施计划

> **For agentic workers:** 本文是经过用户确认的方向性开发基线，不代表已经开始代码实现。实现时按单线程推进，不派发智能体、不创建额外 worktree；每个阶段先测试、再实现、再验证和提交。

**Goal:** 建立一个本地优先的面试复盘辅助机器人，支持上传文字或面试录音进行分析，将确认后的结果沉淀到可检索知识库，并根据不同岗位 JD 进行有依据的文字/异步语音面试模拟。

**Architecture:** 这是独立于简历自动填写扩展的本地 Web 项目。系统把个人信息、主简历、项目经历和历史面试作为共享知识层，把每次面试的 JD 作为会话专属上下文；RAG 负责文档解析、切分、向量化、过滤检索、引用回溯和回答生成。首版采用异步流程：录音先上传并转写，再进入分析或下一轮提问，不实现实时语音流和多模型 Agent 编排。

**Tech Stack:** React + TypeScript + Vite 前端；Python + FastAPI 后端；SQLite 保存结构化元数据；本地文件系统保存原始资料和音频；Qdrant 保存向量；模型供应商 API 提供文本生成、Embedding 和语音转文字能力。所有供应商能力通过后端 Provider 接口隔离，AI 不可用时资料管理、检索调试和手工复盘仍然可用。

**Spec:** 本文作为初步产品与执行基线；正式实现前由本文拆出经过用户确认的独立 spec 和逐任务执行计划。

## 全局约束

- 项目建议独立创建于 `/Users/bytedance/Study/vibe/interview-debrief-bot`，不把语音、RAG 和长文本逻辑写入简历自动填写扩展的 `form-runtime`。
- 个人信息、简历、面试录音、转写和知识库默认只保存在本地；未经用户明确操作不上传、不外发、不自动同步。
- 云端模型只接收当前处理所需的资料、检索片段或音频；完整仓库、Cookie、Token、密码和公司内部敏感数据不得默认发送。
- API Key 只放在后端环境变量或本地 secret 机制中，不能进入前端 bundle、Git、日志或聊天内容。
- 每条正式知识必须区分 `verified`、`needs_review` 和 `rejected`；模型输出、机器转写和历史面试抽取结果默认不是已确认事实。
- 含数字、规模、性能、个人贡献和面试结论的内容必须带来源引用，或显示为待确认。
- 当前核心目标是异步录音/文字分析、RAG 检索和 JD 定制面试；实时语音、多模型编排、账号系统和云端协作不进入首版。
- 删除原始音频、资料、转写或知识条目前必须展示影响范围并要求确认。

## 1. 背景和问题定义

用户希望把多次秋招面试变成持续积累的个人训练数据：个人信息、简历、项目经历和过去的面试内容应该长期共享；每场新面试只变化当前岗位 JD。机器人需要帮助完成三件事：

1. 把上传的录音或文字变成可读的面试记录和问题分析。
2. 根据当前 JD 和共享个人资料进行有针对性的模拟面试。
3. 把新发现的问题、知识缺口和有效回答沉淀回知识库，供之后检索和训练。

系统必须解决两个相反风险：

- 如果不使用 RAG，模型会忘记用户自己的经历，或把多个岗位的要求混在一起。
- 如果直接把所有资料塞进 Prompt，成本、上下文长度、隐私和可解释性都会失控。

因此 RAG 不是附加功能，而是系统的核心数据链路和面试时可以解释的技术亮点：

```text
资料导入 → 解析/转写 → 清洗切分 → Embedding → 向量库
                                              ↓
当前问题 + 当前 JD → 检索与过滤 → 带引用上下文 → 模型回答
                                              ↓
                                   用户确认后回写知识库
```

## 2. 产品边界

### 2.1 首版必须支持

- 上传或粘贴个人信息、主简历和岗位 JD。
- 上传文字版面试记录和面试录音。
- 录音异步转写为文字并保存原始音频、转写状态和转写文本。
- 对资料和转写内容进行切分、向量化、入库和检索。
- 创建一个绑定当前 JD 的面试会话。
- 使用共享个人资料、历史面试和当前 JD 生成文字模拟面试问题。
- 用户用文字回答，机器人继续追问并给出问题依据。
- 对一次面试记录生成复盘报告、问题分类、回答缺口、知识缺口和改进建议。
- 将复盘中提取的知识候选展示给用户确认，确认后再写回共享知识库。
- 导出面试记录、复盘报告和知识库条目为 Markdown/JSON。

### 2.2 首版明确不做

- 不做实时语音通话、流式音频和实时打断。
- 不做多模型 Agent 编排、自动规划多个工具或自主执行任务。
- 不做自动提交求职申请、自动联系 HR 或自动发送面试材料。
- 不把模型生成的经历、指标和个人贡献直接当成事实。
- 不在第一阶段实现云账号、多人协作、跨设备同步和复杂权限系统。
- 不默认上传整个 Git 仓库或公司内部代码。
- 不使用面试评分替代用户判断；评分只是带依据的训练反馈。

## 3. 用户和数据模型

### 3.1 共享个人知识层

共享层在不同面试会话中都可被检索，包括：

- 个人信息；
- 主简历和不同方向简历；
- 教育、实习、工作和项目经历；
- 已确认的项目技术事实、设计取舍和结果；
- 历史面试录音对应的已确认转写和复盘；
- 已确认的知识点、错题和薄弱项；
- 用户手工维护的标准自我介绍和回答素材。

共享层中的每条资料必须有来源和状态。原始资料、转写结果、模型抽取候选和用户确认后的知识条目需要区分存储。

### 3.2 当前面试会话层

每个会话包含：

- 公司名称和岗位名称；
- 当前 JD 原文和解析后的要求；
- 面试类型和轮次；
- 本场问题、回答、追问和分析；
- 本场上传的录音或文字；
- 本场生成的复盘报告；
- 待用户确认的知识候选和知识缺口。

当前 JD 只属于当前会话。默认检索规则是“共享个人层 + 当前会话层”，不自动检索其他岗位的 JD，防止不同公司的要求互相污染。

### 3.3 建议实体

```text
UserProfile
  id, fields, resumeVersions, updatedAt

SourceDocument
  id, kind, title, originalPath, mimeType, scope, status, createdAt

Transcript
  id, sourceDocumentId, text, segments, provider, status, confidence

KnowledgeItem
  id, scope, title, content, tags, sourceDocumentIds, status, verifiedAt

KnowledgeChunk
  id, knowledgeItemId, text, ordinal, tokenCount, embeddingRef, metadata

JobDescription
  id, company, role, rawText, requirements, sourcePath, createdAt

InterviewSession
  id, jobDescriptionId, mode, status, sharedKnowledgePolicy, createdAt

InterviewTurn
  id, sessionId, speaker, inputText, audioDocumentId?, questionType, citations

DebriefReport
  id, sessionId, strengths, weaknesses, gaps, recommendations, citations, status

KnowledgeCandidate
  id, sessionId, claim, proposedContent, sourceIds, status, reviewedAt
```

其中 `scope` 至少区分 `shared` 和 `session`；`status` 至少区分 `draft`、`verified`、`needs_review` 和 `rejected`。

## 4. 主要功能

### 4.1 资料导入和管理

支持以下输入方式：

- 粘贴个人信息和文字材料；
- 上传 Markdown、TXT、PDF 或 DOCX 简历；
- 上传面试录音；
- 粘贴或上传岗位 JD；
- 导入过去的文字面试记录。

导入后显示文件名、来源、解析状态、所属范围和是否已经进入检索库。资料修改后要生成新版本或重新索引，不能静默覆盖旧版本。

### 4.2 音频转写

音频处理采用异步任务：

```text
上传音频 → 保存原文件 → 创建任务 → 语音转文字 → 保存转写
                                      ↓
                              用户检查/修正
                                      ↓
                               允许进入 RAG
```

首版只要求单人或普通面试录音的可读转写，不承诺完美的说话人分离。转写结果要保留时间片段、原始文本、修正文本、模型来源和失败原因。

### 4.3 JD 解析

JD 解析结果至少包含：

- 岗位名称和公司；
- 必须技能；
- 加分技能；
- 工作职责；
- 学历和经验要求；
- 可能的面试主题；
- 与个人资料的匹配项和缺口。

原始 JD 必须保留，结构化解析只是派生数据。模型生成问题时应同时使用原始 JD 和结构化要求，避免只依赖模型抽取结果。

### 4.4 RAG 知识库

RAG 流程分为五步：

1. **解析：** 将简历、JD、文字记录和转写转换成带来源的规范文本。
2. **切分：** 按标题、段落、问答轮次和语义边界切分；保留文档 ID、段落序号、时间戳和作用域。
3. **向量化：** 使用 Embedding Provider 生成向量，保存模型名和维度。
4. **检索：** 根据当前 JD、当前问题和会话阶段检索共享层与当前会话层，并使用 metadata filter 限制范围。
5. **生成：** 将检索片段、来源信息和回答约束注入模型，要求输出回答、引用、未知项和下一步追问。

检索结果必须能在 UI 中展开查看来源。没有检索到足够证据时，机器人应明确说资料不足并要求用户补充，不应用常识填充个人经历。

### 4.5 文字模拟面试

首版以文字交互为主：

- 选择一个 JD 和面试类型；
- 机器人生成第一题；
- 用户文字回答；
- 机器人基于 JD、个人资料和回答继续追问；
- 每一轮保存问题、回答、引用和缺口；
- 用户可以暂停、跳过、重答或结束会话。

问题类型至少包括：

- HR 和动机；
- 简历逐项追问；
- 项目介绍；
- 技术原理；
- 系统设计；
- 故障排查；
- 行为面试；
- JD 定制问题。

问题生成不采用固定题库完全随机抽题，而是使用“岗位要求 + 个人资料 + 历史薄弱点 + 当前回答”进行受控生成，并保留问题来源。

### 4.6 异步语音模拟

实时语音不进入首版，但可以支持低复杂度的异步语音回合：

1. 机器人以文字显示问题。
2. 用户录制一段回答并上传。
3. 后端转写回答。
4. 机器人分析转写并返回文字追问。

这种模式复用音频上传和 STT 管线，不需要实时音频连接、流式打断或 TTS。TTS 如果以后增加，只作为独立输出层，不改变面试会话和 RAG 数据模型。

### 4.7 面试复盘

复盘报告至少包含：

- 面试基本信息；
- 面试官问题列表；
- 用户回答摘要；
- 回答中的优势；
- 回答缺失的背景、职责、方案、结果或数据；
- 技术概念错误或不确定项；
- 没有证据支撑的陈述；
- JD 要求覆盖情况；
- 可能继续追问的方向；
- 建议补充的知识点和资料；
- 下一次练习建议。

报告中的每项判断都应带引用或明确标记为模型建议，不能输出无依据的确定性结论。

### 4.8 知识回写

复盘结束后，系统把可能值得长期保留的内容生成候选：

- 新的项目事实；
- 新的面试问题；
- 用户回答中的常见错误；
- 需要复习的知识点；
- 更好的回答结构；
- 需要补充的证据。

候选先进入待确认列表。用户确认后才写入 `shared` 知识层并重新切分、Embedding 和入库。用户拒绝的候选必须保留拒绝状态，避免下一次重复推荐同一内容。

## 5. 技术实现方式

### 5.1 前端

前端建议使用 React + TypeScript + Vite，页面分为：

- 资料中心：个人资料、简历、历史录音和文字资料；
- 知识库：文档、条目、来源、状态和检索调试；
- 岗位中心：JD 列表和岗位要求解析；
- 面试会话：文字模拟、异步语音回合和会话时间线；
- 复盘页面：报告、引用、知识候选和确认操作；
- 设置页面：模型 Provider、数据目录、索引状态和隐私选项。

前端不直接调用模型 API，不持有 API Key。上传、任务状态、检索和生成统一通过后端 API 完成。

### 5.2 后端

后端建议使用 Python + FastAPI，职责包括：

- 文件上传和本地文件管理；
- PDF/DOCX/TXT/Markdown 解析；
- 音频转写任务；
- 文档规范化、切分和索引；
- Qdrant 检索和 metadata filter；
- Prompt 组装和结构化输出校验；
- 面试会话状态和复盘报告保存；
- 知识候选确认后的回写；
- Provider 错误、超时和重试状态。

首版不引入 Celery、Redis 或消息队列。较短任务可用 FastAPI 后台任务，较长音频用本地任务表记录 `queued/running/succeeded/failed` 状态；当任务量和部署方式确实需要时再升级队列。

### 5.3 存储

- SQLite：用户资料元数据、文档索引、会话、问题、回答、复盘报告、任务状态。
- 本地文件系统：原始简历、JD、音频、转写导出和 Markdown/JSON 备份。
- Qdrant：知识块向量、作用域、文档来源、版本和标签。
- 不把原始音频或完整简历内容写入 Git。

SQLite 与 Qdrant 的记录必须带 schema version。导入和删除要保持元数据与向量库的一致性，索引失败时显示待处理状态，不能伪装成已入库。

### 5.4 Provider 抽象

至少隔离以下接口：

```text
TextGenerationProvider.generateStructured(input, schema)
EmbeddingProvider.embed(inputs)
SpeechToTextProvider.transcribe(audioPath)
```

首版可以使用同一家云服务商提供文本、Embedding 和 STT，也可以分别配置。Provider 只负责外部模型调用，领域层负责会话、证据、引用和回写规则，避免供应商 SDK 侵入核心业务。

### 5.5 RAG Prompt 输出

模型输出建议使用结构化 JSON，至少包含：

```text
answer              当前回答或反馈
nextQuestion        下一道问题或追问
questionType        问题类型
citations           使用的知识块和来源
unsupportedClaims   无证据支撑的内容
knowledgeGaps       需要补充的知识点
confidence          模型自报置信度，仅作提示
```

后端必须校验 JSON schema。引用 ID 不存在、引用不属于当前检索上下文或生成内容含有未确认个人事实时，标记为需要复核，不直接进入正式知识库。

## 6. 所需外部资源和配置

### 6.1 云端方案

最小云端配置通常需要：

- 文本模型 API Key：JD 分析、面试问题、回答分析和复盘报告；
- Embedding API Key：知识库向量化；可以与文本模型使用同一供应商，也可以分开；
- 语音转文字 API Key：录音转写；
- 本地 Qdrant：向量检索；
- 本地磁盘：保存原始音频、简历和转写；
- 麦克风权限：仅在录制异步回答时需要。

首版不需要 TTS API Key，因为不做实时语音，也可以先由机器人返回文字问题。以后需要语音播报时再增加 TTS Provider。

建议的配置形态：

```text
LLM_API_KEY=只存在后端环境
LLM_BASE_URL=模型服务地址
LLM_MODEL=文本模型名
EMBEDDING_API_KEY=可选，默认复用后端模型配置
EMBEDDING_MODEL=向量模型名
STT_API_KEY=语音转文字服务密钥
QDRANT_URL=http://127.0.0.1:6333
DATA_DIR=本地资料目录
```

具体变量名在实现阶段统一定义；绝不把真实值写入仓库或交给其他模型。

### 6.2 完全本地方案

不使用云端 API 也可以运行，但需要本机部署文本模型、Embedding 模型和 Whisper 类 STT 模型，并承担模型下载、显存/内存、速度和效果波动。它更适合隐私优先场景，不作为首版默认路径。

## 7. 分阶段开发计划

### 阶段 0：独立项目基线

目标：创建独立目录和 Git 仓库，确定配置、数据目录、隐私边界和 Provider 接口。

产出：前后端骨架、SQLite 初始化、Qdrant 本地连接、`.env.example`、数据目录忽略规则、健康检查和最小页面。

验收：不配置模型 Key 也能启动、查看健康状态和管理空知识库；敏感文件不会被 Git 跟踪。

### 阶段 1：资料、JD 和会话模型

目标：先把“共享个人资料 + 当前 JD + 面试会话”三层关系建立起来。

产出：资料上传、JD 创建、会话创建、版本化元数据、基础列表和详情页面。

验收：创建两个不同 JD 的会话时，共享个人资料可复用，但一个会话的 JD 不会被另一个会话检索到。

### 阶段 2：文档解析、音频转写和索引

目标：建立可追踪的异步 ingestion pipeline。

产出：PDF/DOCX/TXT/Markdown 解析、音频上传、STT 任务、转写修正、规范文本、切分、Embedding 和 Qdrant 入库。

验收：一份资料从上传到可检索有明确状态；任务失败能显示原因并允许用户重试；每个知识块能回到原始文档、段落或音频时间片段。

### 阶段 3：RAG 检索与可引用生成

目标：让机器人能够基于证据回答，而不是只靠模型常识。

产出：作用域过滤、向量检索、检索调试页、带来源 Prompt、结构化输出和引用展示。

验收：输入一个关于个人经历的问题，返回结果包含正确来源；切换 JD 后问题方向变化，但个人资料仍然可被检索；没有证据时明确提示资料不足。

### 阶段 4：文字模拟面试

目标：完成第一个可持续使用的面试会话闭环。

产出：按 JD 生成问题、文字回答、追问、会话暂停/继续、每轮引用和问题类型。

验收：同一个人资料下创建两个不同 JD 会话，问题主题有明显差异；每轮问题都能显示来源 JD、个人资料或历史薄弱点；模型失败时会话记录不丢失。

### 阶段 5：录音复盘和异步语音回合

目标：把真实面试录音纳入分析和训练。

产出：录音转写、问题/回答分段、复盘报告、异步语音回答、转写修正和报告引用。

验收：上传一段虚构测试录音后可以得到转写和复盘；转写错误可以人工修改并重新索引；不会把录音分析误写成用户确认事实。

### 阶段 6：知识候选和学习闭环

目标：让每次面试都能改进下一次准备。

产出：知识候选、知识缺口、确认/拒绝、重新索引、训练建议和 Markdown/JSON 导出。

验收：用户确认的知识进入共享层并能被后续 JD 会话检索；拒绝的候选不进入正式检索；每个缺口能追溯到具体面试问题或回答。

### 阶段 7：与投递工作台关联

目标：把岗位管理和面试准备连接起来，但保持两个工具独立可用。

产出：岗位 ID、项目/简历引用、待准备问题、面试轮次和复盘链接；优先使用版本化 JSON 导入导出，不先做实时通信。

验收：投递工作台中的岗位可以关联一个面试会话；面试机器人可以引用岗位和简历版本；任一工具单独运行时核心功能不受影响。

## 8. 测试和质量标准

### 单元测试

- 文档解析和格式错误；
- 文档切分和元数据继承；
- shared/session 作用域过滤；
- 任务状态转换；
- 引用校验和未验证内容拦截；
- Prompt 输入和结构化输出 schema；
- 知识候选确认、拒绝和回写；
- Provider 超时、错误和空响应。

### 集成测试

- 使用 fake Text/Embedding/STT Provider 验证完整 ingestion pipeline；
- 使用本地 Qdrant 测试写入、过滤检索和删除；
- 验证当前 JD 不会检索到其他会话 JD；
- 验证报告引用的 source ID 确实存在；
- 验证索引失败不会把文档状态标为 ready。

### E2E 测试

使用虚构简历、虚构 JD 和测试音频覆盖：

- 上传资料并建立共享知识库；
- 创建不同 JD 的两个会话；
- 文字面试和追问；
- 音频转写和复盘；
- 查看引用；
- 确认知识候选后在下一场会话中检索到；
- 删除资料后相关向量和引用失效。

### RAG 评估

建立一组小型、人工确认的评估问题，至少测量：

- 检索是否命中预期来源；
- 引用是否覆盖回答中的关键事实；
- 无证据时是否拒绝猜测；
- 不同 JD 下是否检索到正确的岗位上下文；
- 新旧知识回写后结果是否发生预期变化。

这些指标用于判断 RAG 是否真的工作，也可以作为面试中介绍项目时的量化证据；不能只用“模型回答看起来不错”作为验收。

## 9. 面试时可以讲清楚的技术亮点

这个项目可以作为面试项目，但需要讲真实实现和验证过的部分。重点可以围绕：

- 为什么把共享个人资料和会话 JD 分层；
- 为什么选择 RAG，而不是把所有资料拼进 Prompt 或直接微调；
- 文档、转写和知识条目的生命周期；
- chunk metadata 如何保留来源、作用域和版本；
- 如何避免不同岗位 JD 互相污染；
- 如何处理模型幻觉、无证据回答和用户贡献误判；
- 为什么音频采用异步任务而不是实时流；
- 如何设计 Provider 抽象，避免绑定单一模型供应商；
- 如何用检索命中率、引用覆盖率和无证据拒答测试 RAG；
- 如何在隐私和模型效果之间取舍。

不能把“支持多模型 Agent”“实时语音”“自动理解所有项目”写进简历，除非后续确实实现并验证。

## 10. 风险和处理原则

### 隐私风险

简历、个人信息和录音都属于敏感资料。默认本地保存，模型调用前做最小上下文选择；日志只记录任务 ID、耗时和错误类型，不记录原文和音频内容。

### 事实真实性风险

模型可能把推测写成经历。所有长期知识先经过候选和用户确认，数字、贡献和结果必须能回到来源。

### 转写错误风险

专业名词、公司名和技术栈容易被 STT 误识别。转写结果可编辑，未修正的转写只能作为待复核来源。

### 检索污染风险

把其他岗位 JD 或错误复盘写入共享层会影响后续面试。使用 `shared/session` 作用域、版本和用户确认状态控制写回。

### 成本和延迟风险

上传音频、Embedding 和长上下文都会产生费用和等待时间。首版采用异步任务、局部检索、短 Prompt 和缓存，不做实时语音。

### 项目范围风险

先完成“资料 → RAG → 文字模拟 → 音频复盘 → 知识回写”闭环，再考虑 TTS、云同步和更多模型。任何新增能力都不能破坏本地核心流程。

## 11. 首版完成定义

满足以下条件才算首版完成：

1. 用户可以上传个人资料、简历、一个或多个 JD、文字记录和音频。
2. 音频可以异步转写，转写内容可以人工修正。
3. 资料和转写内容可以进入带作用域和来源的 RAG 知识库。
4. 不同 JD 会话使用共享个人资料，但不会混用其他会话的 JD。
5. 文字模拟面试能够根据 JD 提问、追问并保存完整会话。
6. 录音或文字面试能够生成带引用的复盘报告。
7. 复盘结果先进入知识候选，用户确认后才写回共享知识库。
8. 没有 API Key、模型超时或检索失败时，系统能保留资料和会话状态并明确报错。
9. 核心流程不依赖实时语音、多模型编排、后端云部署或账号系统。
10. 有自动化测试和至少一组 RAG 检索/引用评估证据。

## 12. 当前结论

该项目可行，且比单纯的面试问答机器人更适合作为面试项目：它有明确的数据分层、真实的 RAG 链路、异步音频处理、引用和知识回写闭环。首版应优先把“可追溯的 RAG + 文字面试 + 录音复盘”做扎实，实时语音和多模型编排保持在范围之外。
