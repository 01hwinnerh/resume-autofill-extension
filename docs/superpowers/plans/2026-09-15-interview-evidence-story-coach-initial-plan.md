# 面试项目证据库与故事教练初步实施计划

> **对接手开发者：** 本文是经过初步讨论的产品与实现方案，不代表已经获得代码实现授权。实现前必须先确认第一阶段范围，并按单线程、无额外 worktree 的方式逐项执行和验证。

**Goal:** 建立一个本地优先的面试项目证据库，把真实项目事实、代码证据、面试故事和追问训练组织成可复用的面试准备系统。

**Architecture:** 工具作为独立的本地 Web 项目存在，与简历自动填写扩展通过岗位、项目引用和版本化导入导出协议关联。它不进入浏览器页面 runtime；扩展负责当前岗位和投递操作，证据库负责长文本编辑、项目事实管理、故事版本和训练记录。AI 不是基础依赖，所有核心功能先用结构化表单、模板和人工确认实现。

**Tech Stack:** React、TypeScript、Vite、IndexedDB 或等价的本地持久化层；Markdown/JSON 导出；可选的本地 Git 证据读取器。实现阶段沿用当前项目的 TypeScript、Vitest、Playwright 和本地优先原则，但不强制与浏览器扩展共享运行时。

**Spec:** 本文同时承担初步产品设计和实现路线说明；正式开发前从本文确认第一阶段范围，再拆分独立的正式 spec 和执行计划。

## 1. 背景与要解决的问题

秋招面试的主要损耗不是没有项目，而是项目事实分散在代码、提交记录、文档、聊天记录和个人记忆中，导致以下问题：

- 简历上的项目描述无法快速对应到真实代码证据；
- 面试时讲不清自己负责的边界、数据流和设计取舍；
- 同一个项目无法快速生成 1 分钟、3 分钟和技术深挖版本；
- 面试官追问失败原因、替代方案和指标时，只能临时回忆；
- 每次面试后的问题和薄弱点没有沉淀，下一次仍然重复暴露；
- AI 生成的表达可能混入没有证据支撑的指标或经历。

工具的核心目标不是“替用户编造一个更好听的故事”，而是把真实经历整理成可核验、可复述、可追问的面试资产。

## 2. 产品目标与非目标

### 2.1 产品目标

- 为每个项目建立事实、证据、故事和问题的统一入口。
- 每条重要结论都可以关联到代码文件、提交、测试、命令输出、文档或用户手工确认。
- 支持不同岗位和面试轮次使用不同故事版本。
- 用结构化追问训练提升项目表达和技术深挖能力。
- 记录面试后真实暴露的知识缺口，服务后续学习计划。
- 保持本地优先，默认不上传项目代码、个人资料或公司信息。

### 2.2 非目标

- 不自动判定用户是否真正掌握某项技术；掌握度需要用户作答或完成可验证练习。
- 不把 AI 输出直接当作简历事实或面试事实。
- 不自动读取并上传整个代码仓库到远程模型。
- 不替代简历编辑器、投递平台或在线面试软件。
- 不在第一阶段实现账号、后端、团队协作、云同步和复杂 RAG。

## 3. 核心用户流程

### 流程 A：建立项目档案

1. 用户创建项目，填写项目背景、目标、时间、角色、技术栈和个人负责范围。
2. 用户添加项目结果、指标、设计决策、故障和改进项。
3. 每条事实绑定一个证据来源，或明确标记为“待验证”。
4. 工具显示项目事实完整度和未验证风险。

### 流程 B：生成面试故事

1. 用户选择项目和目标场景，例如“项目介绍”“技术难点”“故障排查”“系统设计取舍”。
2. 工具按模板组织背景、任务、行动、结果、反思和追问点。
3. 用户编辑成自己的表达，保存 1 分钟、3 分钟和深挖版本。
4. 工具在没有证据的句子旁显示待核验提示。

### 流程 C：面试训练与复盘

1. 用户选择岗位、项目和故事版本。
2. 工具随机或按主题提出主问题和连续追问。
3. 用户填写或录入自己的回答，并标记“能独立回答 / 需要提示 / 不会”。
4. 工具记录回答结构、缺失证据、技术缺口和下一次练习内容。
5. 用户面试后补充真实问题，形成新的题目和复盘记录。

## 4. 功能范围

### 4.1 项目档案

每个项目包含：

- 项目名称和一句话定位；
- 背景、目标、用户或业务场景；
- 起止时间和个人角色；
- 技术栈与关键依赖；
- 个人负责范围；
- 架构、模块和数据流；
- 结果、指标和影响；
- 失败经历、限制和后续改进；
- 关联简历版本、目标岗位和面试记录。

### 4.2 证据条目

证据条目不是完整源代码副本，而是支持某条事实的最小引用。建议支持以下来源类型：

- `file`：文件路径和行号范围；
- `commit`：Git commit SHA 和提交说明；
- `test`：测试文件、测试名和运行命令；
- `command`：可复现命令和经过脱敏的关键输出；
- `metric`：指标来源、计算方式和验证状态；
- `document`：项目文档标题和本地路径；
- `manual`：用户明确确认的事实，要求标注确认时间。

每条证据至少包含：

```text
claim       要支持的事实
sourceType  来源类型
locator     文件/commit/命令等定位信息
excerpt     最小必要的脱敏片段
status      verified | needs_review | rejected
```

### 4.3 故事卡片

故事卡片包含：

- 使用场景和目标岗位；
- 目标时长；
- 开场背景；
- 个人任务和边界；
- 采取的方案；
- 关键技术细节；
- 结果和指标；
- 设计取舍；
- 失败与修复；
- 面试官可能追问；
- 对应证据；
- 最后一次练习时间和自评。

模板至少覆盖：

- 1 分钟项目介绍；
- 3 分钟完整项目介绍；
- 一个技术难点；
- 一次故障排查；
- 一次设计取舍；
- 一次失败复盘；
- “如果重新设计”问题。

### 4.4 题目和追问树

题目按项目、岗位、技术主题和面试轮次组织。每个主问题可以有多个追问分支，例如：

```text
项目为什么这样设计？
├── 有没有替代方案？
├── 这个方案的瓶颈是什么？
├── 出现故障时怎么定位？
├── 数据量扩大十倍怎么办？
└── 你个人具体负责哪部分？
```

题目答案只保存用户自己的回答、证据关联和复盘结论，不把工具生成的草稿自动标记为已掌握。

### 4.5 训练记录

每次训练记录：

- 使用的岗位和项目；
- 使用的故事版本；
- 主问题和追问路径；
- 用户回答；
- 是否独立完成；
- 暴露的知识缺口；
- 需要补充的证据；
- 下一次练习建议。

训练结果可以导出为面试复盘 Markdown，但不自动写入最终简历或对外材料。

### 4.6 与投递工作台的关联

后续可以让投递工作台引用：

- 某个岗位需要准备的项目故事；
- 该岗位使用的简历版本；
- 该岗位的高频问题；
- 面试轮次和复盘记录。

这种关联使用项目 ID、岗位 ID 和导入导出数据建立，不把面试证据库的长文本逻辑放进自动填写插件的页面 runtime。

## 5. 数据模型初稿

建议的核心实体：

```text
Project
  id, title, summary, role, timeRange, stack, responsibility, status

EvidenceItem
  id, projectId, claim, sourceType, locator, excerpt, status, verifiedAt

Story
  id, projectId, scenario, targetRole, duration, sections, evidenceIds, status

Question
  id, projectId?, role?, category, prompt, followUps, expectedEvidenceIds

PracticeSession
  id, jobId?, projectId?, storyId?, questionIds, answers, selfAssessment, gaps, createdAt

JobContext
  id, company, role, source, resumeVersion, projectIds, interviewStage
```

数据约束：

- `EvidenceItem.status = verified` 只能由用户确认或明确的本地验证流程产生。
- 含有数字、性能、规模和结果的故事句子必须有证据或标记为 `needs_review`。
- `Story` 可以保存草稿，但导出对外材料前必须显示未验证项。
- 删除项目时必须明确展示将要删除的故事、证据和训练记录。
- 导入数据必须先预览新增、覆盖、冲突和删除，不直接覆盖现有资料。

## 6. 实现方式

### 6.1 工具形态

推荐创建独立项目目录：`/Users/bytedance/Study/vibe/interview-evidence-coach`。

第一阶段使用本地 Web 应用：

- React 页面负责项目、证据、故事和训练界面；
- TypeScript 领域层负责数据校验、故事模板和状态转换；
- IndexedDB 保存结构化数据和版本信息；
- Markdown/JSON 作为可读、可备份、可迁移的导出格式；
- 不依赖后端、账号、远程数据库或 AI 服务。

### 6.2 证据采集

第一阶段支持手工添加证据；第二阶段增加本地 Git 读取器。Git 读取器只生成“候选证据”，不自动把 commit 说明当成用户个人贡献。用户需要确认：

- 这项工作是否由本人完成；
- 个人贡献边界是什么；
- 结果和指标是否真实；
- 哪些代码或测试可以公开讲解。

读取器必须支持脱敏和拒绝导入，避免把公司内部代码、内部 URL、配置、Token 和业务数据写入证据库。

### 6.3 故事生成

P0 不使用 AI 自动写故事。工具提供结构化编辑器和模板，将用户已确认的证据填入对应段落，并把缺失字段显示为待补充。

后续 AI 若接入，必须通过独立的 `StoryDraftProvider` 接口提供草稿，输出必须保留证据引用和未验证标记，用户确认前不能进入可导出内容。AI 失败时，结构化编辑器必须仍然可用。

### 6.4 与现有扩展的通信

第一阶段不做实时通信。先约定可版本化的 JSON 导出格式，投递工作台和面试证据库通过项目 ID、岗位 ID 和简历版本 ID 建立弱关联。

后续若确实需要一键联动，再增加扩展侧“打开项目故事”和“把当前岗位加入准备清单”入口；仍然由工作台页面负责长文本编辑和训练，不把它们塞进表单 runtime。

## 7. 分阶段计划

### 阶段 0：确认边界和数据协议

产出：项目目录、数据实体、证据状态、导入导出格式和隐私规则。

完成标准：可以解释每个字段的来源、生命周期和删除行为；不存在“AI 自动判定真实经历”的隐含要求。

### 阶段 1：项目档案和证据库

产出：项目 CRUD、证据条目 CRUD、证据状态和项目完整度视图。

完成标准：用户可以创建一个虚构项目，添加文件、commit、测试和手工证据，并能筛出未验证事实。

### 阶段 2：故事卡片和版本

产出：1 分钟、3 分钟、技术难点、故障排查、设计取舍等故事模板；故事与证据关联；导出 Markdown。

完成标准：每个故事可以从证据跳回来源；含无证据数字的句子会被标记；导出内容不会混入未确认事实。

### 阶段 3：追问训练和复盘

产出：题目管理、追问树、训练会话、自评、薄弱点和复盘导出。

完成标准：完成一次主问题加两级追问，能够看到回答、证据、缺口和下一次训练建议。

### 阶段 4：本地仓库证据导入

产出：选择性读取 Git commit、文件和测试引用；候选事实预览；脱敏和用户确认。

完成标准：导入只生成候选条目，不自动宣称个人贡献；拒绝条目不会进入可导出故事。

### 阶段 5：与投递工作台关联

产出：岗位关联项目、简历版本、故事和训练记录；从投递工作台打开准备材料。

完成标准：用户打开一个岗位时能看到待准备项目和故事，但两个工具仍能独立运行和导出。

### 阶段 6：可选 AI 增强

产出：基于已确认证据的故事草稿、追问候选和表达压缩建议。

完成标准：AI 不可用时核心流程不受影响；每条生成内容可追溯到证据；用户确认前不得对外导出。

## 8. 验收标准

- 用户可以创建和维护多个项目档案。
- 项目事实可以关联到最小必要证据。
- 未验证事实和无来源数字会被显式标记。
- 用户可以保存多个场景和时长的故事版本。
- 故事可以生成 Markdown/JSON 导出，并保留证据引用。
- 用户可以进行主问题和追问训练，并保存回答和复盘。
- 删除、导入和覆盖操作都有明确预览或确认。
- 本地数据可以备份和恢复。
- 不上传完整仓库，不保存凭据，不自动制造个人贡献。
- 不依赖 AI、后端或云账号也能完成 P0 核心流程。

## 9. 风险和取舍

### 证据真实性风险

Git commit 或文档只能证明某项变更存在，不能单独证明用户亲自完成了全部工作。解决方式是将机器读取结果标记为候选，并要求用户确认个人贡献边界。

### 敏感信息风险

公司代码、内部数据和配置可能出现在仓库或命令输出中。默认只保存路径、行号和经过用户确认的最小片段，提供拒绝导入和脱敏入口。

### 过度依赖 AI

AI 可能生成流畅但不真实的故事。P0 使用结构化模板和证据引用，AI 只作为后续可替换的草稿提供者。

### 工具过度复杂

如果第一阶段同时加入岗位管理、知识库、语音识别、云同步和 RAG，项目会失去验证重点。第一阶段只做“项目事实 → 证据 → 故事 → 导出”。

### 与浏览器扩展耦合过深

面试证据库需要长文本编辑和训练记录，与页面注入生命周期不同。保持独立应用，通过版本化数据协议关联，可以降低扩展发布和数据迁移风险。

## 10. 当前结论

面试项目证据库与故事教练应作为独立的本地优先工具开发，同时预留与秋招投递工作台的项目、岗位和简历版本关联。它的第一价值是建立“真实事实和证据链”，第二价值才是生成故事和训练追问；AI 可以延后，不应阻塞第一阶段交付。
