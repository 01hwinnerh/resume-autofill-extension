# 通用半自动简历投递扩展：已确认设计基线

## 文档状态

- 状态：已确认设计基线
- 确认日期：2026-09-14
- 适用项目：通用半自动简历投递浏览器扩展
- 变更规则：后续开发必须遵守本文已确认的目标和边界；如需改变核心行为，应先更新设计并重新确认。

## 1. 项目目标

开发一个面向不同岗位、不同招聘网站和不同公司类型的通用半自动简历投递扩展，用于减少重复填写个人信息的时间。

项目不限制前端、后端、AI、互联网、私企、国企等岗位类型。岗位差异由个人资料版本、求职偏好和开放题答案库表达；网页结构差异由通用表单引擎、招聘平台 Adapter 和用户自定义映射处理。

首版以 Chrome/Edge 桌面浏览器扩展为主要形态，采用本地优先的资料处理方式，不依赖外部服务即可完成基础字段填写。

## 2. 产品边界

### 2.1 首版需要支持

- 用户配置个人资料；
- 扫描当前招聘页面的表单；
- 识别普通输入框、文本域、下拉框、单选框和复选框；
- 将网页字段匹配到标准个人资料字段；
- 展示匹配结果和置信度；
- 用户确认后批量填写；
- 默认只填写空字段，不覆盖已有内容；
- 填写后重新校验页面是否接收了目标值；
- 展示未识别、暂不支持和填写失败的字段；
- 保存用户明确确认过的自定义字段映射。

### 2.2 首版明确不支持或不自动执行

- 自动点击最终提交申请；
- 绕过验证码、短信验证、登录、OAuth 或其他反自动化机制；
- 自动选择本地文件并上传简历、证书等附件；
- 对不确定的字段进行猜测性填写；
- 将个人资料或页面内容默认上传到远程服务器；
- 按岗位类型写死一套不可扩展的字段模型。

复杂场景可以通过人工确认、用户自定义映射或后续平台 Adapter 增强，但不能突破上述安全边界。

## 3. 核心架构

系统由三层协作：

```text
通用表单引擎
        ↓
招聘平台 Adapter
        ↓
用户自定义映射
```

### 3.1 通用表单引擎

通用表单引擎负责所有招聘页面可能共享的能力：

- 扫描网页控件；
- 读取标签、name、id、placeholder、aria-label、autocomplete、选项和页面区域信息；
- 将页面字段转换成统一的字段描述；
- 使用通用字段词典和类型约束进行匹配；
- 填写普通控件并触发页面所需的输入事件；
- 校验填写结果；
- 管理字段状态和局部失败。

运行时字段句柄允许一个逻辑字段关联多个 DOM 元素：普通控件关联一个元素，radio 组关联该组的全部选项。跨扩展上下文传输时仍只发送不含 DOM 元素的 `PageFieldDescriptor`。

通用引擎不包含具体公司的选择器和页面流程。

### 3.2 招聘平台 Adapter

Adapter 负责特定招聘平台或页面结构的特殊行为：

- 判断当前页面是否属于该平台；
- 定位平台特有字段；
- 操作自定义下拉框等特殊控件；
- 处理多步骤页面和动态加载；
- 提供平台特有的填写校验方式。

Adapter 按平台或页面结构组织，不按前端、后端、国企等岗位组织。一套平台 Adapter 可以覆盖多个使用相同招聘系统的公司。

Adapter 应优先采用配置化规则，只有复杂控件才增加专用逻辑。Adapter 失效时必须回退到通用引擎，而不是导致扩展整体不可用。

### 3.3 用户自定义映射

用户自定义映射负责处理通用规则和 Adapter 都无法确定的字段，也可以覆盖不准确的自动判断。

示例：

```text
页面字段“是否服从调剂”
    → custom.acceptAdjustment
    → 默认值“是”
```

用户明确保存的映射优先级最高。映射应尽量绑定到平台、域名、字段特征和页面区域，避免某个网站的规则错误应用到其他网站。

字段匹配优先级：

```text
用户明确映射 > 平台 Adapter > 通用匹配规则 > 人工处理
```

## 4. 个人资料模型

个人资料和网页字段分离。个人资料保存事实，网页字段保存当前页面的要求，映射关系负责连接二者。

标准资料模型包含以下可扩展分类：

```text
基础身份
联系方式
教育经历[]
工作/实习经历[]
项目经历[]
技能与证书
求职偏好
资格与声明
附件
开放题答案
自定义字段
```

字段需要具备类型和填写策略，例如：

```text
字段类型：文本、日期、数字、枚举、布尔、多选、长文本、文件
填写策略：自动填写、填写前确认、永不自动填写
```

具体个人信息和最终标准字段清单不在本设计基线中提前固化，后续单独确认。

## 5. 用户交互流程

扫描和填写必须分为两个动作，扫描阶段不能修改网页：

```text
空闲
  ↓
扫描页面
  ↓
展示匹配结果
  ↓
用户确认
  ↓
开始填写
  ↓
重新校验
  ↓
完成 / 部分完成 / 失败
```

侧边栏至少展示以下分类：

```text
已识别并可填写
需要确认
页面已有值并已跳过
暂不支持
填写失败
```

默认交互规则：

- 页面已有内容时不覆盖；
- 只有用户确认过的字段才允许填写；
- 高风险字段需要单独确认；
- 一个字段失败不能回滚其他已成功字段；
- 不自动导航到不可逆的提交动作；
- 用户手动修改后的内容不能被后续自动操作覆盖；
- 用户明确操作后才保存新的自定义映射。

## 6. 字段状态和异常处理

字段级状态包括：

```text
matched              已匹配
needs_confirmation   需要确认
skipped_existing     页面已有值，已跳过
filled               已写入
verified             已确认网页接收
failed               填写失败
unsupported          暂不支持
```

主要异常都应转化为局部结果：

- 没有网页权限：提示用户授权当前网站；
- 页面没有表单：提示页面可能尚未加载或暂不支持；
- 字段含义不明确：不自动填写；
- 页面动态刷新：重新定位并有限次重试；
- 自定义控件操作失败：标记为手动处理；
- 页面校验失败：展示错误字段和原因；
- 单字段失败：保留其他字段成功结果。

系统遵循“局部失败，不全局失败；无法确认，不猜测填写”的原则。

## 7. 测试原则

测试需要覆盖三层职责：

- 通用匹配器：测试中文、英文、同义字段和类型约束；
- 本地 HTML 测试页面：覆盖普通表单、动态表单、受控组件和自定义下拉框；
- Adapter 测试：确认平台识别、字段定位、特殊控件操作和填写校验；
- 浏览器端到端测试：使用本地模拟招聘页面，不对真实岗位执行提交；
- 真实页面人工验证：验证扫描和填写，不点击最终提交。

每个 Adapter 必须满足：

- 新增 Adapter 不破坏通用引擎；
- Adapter 识别失败时可以回退通用引擎；
- 单字段失败不阻塞其他字段；
- 不能绕过用户确认自动提交；
- 不确定字段可见、可修改、可跳过。

## 8. 后续设计必须遵守的原则

- 先保证通用字段填写的可靠性，再扩展 AI 和批量能力；
- 不用 AI 替代事实字段的确认；
- 不把每家公司写成一套独立核心逻辑；
- 不为了支持少数复杂页面破坏通用引擎；
- 所有自动化都必须可解释、可确认、可局部失败；
- 任何涉及自动提交、验证码绕过、登录凭据或远程保存个人资料的变化，都必须重新进行范围和安全评审。

## 9. 已确认技术方案

### 9.1 技术栈

```text
扩展构建：WXT
界面：React + TypeScript
浏览器规范：Chrome Manifest V3
单元测试：Vitest
浏览器端到端测试：Playwright
资料存储：扩展本地存储
```

React 只用于侧边栏、资料配置页等扩展界面；字段扫描、匹配、填写和校验核心使用纯 TypeScript，避免让界面框架耦合网页 Content Script。

P0 不引入 Node 服务、数据库、Redis、Python 服务或远程 API。具体依赖版本在项目初始化时根据当时的运行环境锁定，版本号不作为本设计基线的固定内容。

### 9.3 AI 的范围

AI 接入是完全可选的未来扩展，不属于 P0、P1 或项目完成条件，也不设置承诺时间表。即使长期不接入 AI，通用字段识别、平台适配、用户映射和半自动填写仍然是完整项目。

如果未来接入 AI，只能用于未知字段辅助判断、答案推荐或开放题草稿，并且必须经过用户确认，不能替代事实字段校验，也不能自动提交申请。

## 10. 开发阶段和验收标准

### 阶段一：扩展骨架

目标：扩展可以在 Chrome 中加载，打开侧边栏和资料配置页，保存模拟资料，并完成扩展 UI 与 Content Script 的通信。

验收标准：扩展正常加载；打开招聘页面时不自动修改页面；用户点击操作后才能开始扫描。

### 阶段二：通用表单引擎

目标：扫描普通表单，识别常见字段，展示匹配结果，用户确认后填写，并校验填写结果。

验收标准：在本地模拟页面中完成文本框、文本域、下拉框、单选框和复选框的填写；已有内容不被覆盖；不确定字段不会自动填写。

### 阶段三：自定义映射和安全交互

目标：支持字段置信度、逐字段确认、自定义字段、平台级映射、敏感字段确认和局部失败。

验收标准：一个字段失败时其他字段仍可成功；用户可以修改、跳过和保存映射；系统不执行最终提交。

### 阶段四：招聘平台 Adapter

目标：接入第一个真实招聘平台，处理动态页面、自定义下拉框和多步骤表单，并在 Adapter 失效时回退通用引擎。

验收标准：真实页面只验证扫描、填写和校验，不执行最终提交；新增 Adapter 不破坏通用引擎测试。

### 阶段五：投递效率增强

目标：支持多套资料版本、开放题答案库、投递记录、快捷操作、填写差异和人工处理清单。

验收标准：用户可以切换资料版本并追踪岗位填写状态，复杂问题仍保留人工确认。

### 阶段六：AI 未来扩展

该阶段没有固定开始时间。只有在核心填写链路稳定且确实存在效率收益时，才重新进行需求、安全和隐私评审。

## 11. MVP 完成定义

MVP 完成需要同时满足：

- 支持一批本地模拟招聘页面；
- 能完成常见字段的一键半自动填写；
- 用户可以查看和修改每个匹配结果；
- 不覆盖已有输入；
- 不确定字段不自动填写；
- 单字段失败不影响整体；
- 不自动提交；
- 不需要后端即可运行；
- 单元测试、浏览器测试和人工页面验证通过。
